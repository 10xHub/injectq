## What is measured, and why

A dependency injection container costs time in four places. Each scenario isolates one of them,
so you can tell which one matters for your application.

| | Cost | Scenario |
|---|---|---|
| 1 | Fetching something already built | S1 |
| 2 | Building an object graph on demand | S2, S3, S6 |
| 3 | Opening and closing a request scope | S4 |
| 4 | Injecting dependencies into a function call | S5 |
| 5 | Setting the container up | S7 |

All numbers are microseconds per operation (lower is better). Every library is compared with the
same objects doing the same work, and with a **hand-written** baseline: plain constructor calls with
no container at all. The baseline is the floor; the "relative to hand-written" column shows what
the container costs on top of it.

The comparison does **not** claim a DI container makes your application faster. A web request
usually spends tens or hundreds of microseconds in the framework, so a container costing 1 µs per
request is rarely what you feel. See the [HTTP benchmark](#http-benchmark) for the end-to-end view.

## The scenarios

The classes are tiny on purpose: constructors only store their arguments, so the measurement is
the container, not your code.

### S1: cached singleton

`Config` is registered as a singleton. Measure `container.get(Config)` after it was created.
Hand-written:

```python
config = Config()
config            # "resolving" it
```

### S2: transient chain

`C` needs `B`, `B` needs `A`; all three are transient, so every resolve builds a fresh `C`, `B`
and `A`. Hand-written:

```python
C(B(A()))
```

### S3: wide graph

`Wide` takes five transient services `D1..D5`, and each `Di` takes its own singleton `Si`.
Every resolve builds `Wide` and five `D`s and reuses the five singletons. Hand-written:

```python
Wide(D1(s1), D2(s2), D3(s3), D4(s4), D5(s5))
```

### S4: request scope

Enter a request scope, resolve `Req` (which needs the singleton `Config`), leave the scope. Inside
one scope `Req` is the same object on repeat; a new scope gets a new one. Hand-written (a
per-request cache, the smallest thing that meets this contract):

```python
class RequestScope:
    def __enter__(self):
        self.cache = {}
        return self.req
    def __exit__(self, *exc):
        self.cache = None
    def req(self):
        r = self.cache.get(Req)
        if r is None:
            r = self.cache[Req] = Req(config)
        return r

with RequestScope() as req:
    req()
```

### S5: injected function call

`f(x1: X1, x2: X2, x3: X3)` where all three are singletons. Measure calling `f()` with no
arguments and letting the library inject them. Hand-written:

```python
f(x1, x2, x3)
```

### S6: async transient chain

The S2 graph, resolved from an async context (`await container.aget(C)` or the library's
equivalent). Hand-written:

```python
async def make_c():
    return C(B(A()))
```

### S7: build a container

Register 50 services in a chain (`K0`, `K1(K0)`, ..., `K49(K48)`) in a fresh container. **S7r**
additionally resolves `K49` once, because some libraries do their graph analysis or code
generation lazily on the first resolve, and building without resolving would hide that cost.
Hand-written:

```python
registry = {k: k for k in K}
obj = registry[K[0]]()
for k in K[1:]:
    obj = registry[k](obj)
```

## Method

- **Same graph, verified.** Every library script resolves its graph through a shared set of checks
  before timing anything (`benchmarks/common.py`, class `Verifier`): types and nesting are right,
  singletons are the same object across resolves, transients are fresh, request scope gives one
  instance per scope and different instances across scopes, the injected function receives the
  right singletons. A failed check aborts the run with a non-zero exit code. A library that
  cannot do something (for example no request scope) is reported as `n/a`, not approximated.
- **Process isolation.** Each library runs in its own Python process, so imports, monkey-patching
  and caches of one library cannot affect another. Classes are created fresh per library.
- **Warm-up and calibration.** One untimed call, then the loop count is calibrated so each repeat
  takes about 20 ms.
- **Repeats and statistic.** The loop is timed `BENCH_REPEATS` times (25 by default); the
  **median** per-operation time is reported. Medians resist the occasional slow repeat caused by
  other processes.
- **Pinned versions.** Library versions are pinned in `benchmarks/compare/requirements.txt` and
  recorded, with the CPU, OS and Python build, in the raw JSON under `benchmarks/results/`.
- **Equivalences that are not 1:1.** Where a library has no direct equivalent, the closest
  idiomatic form is used and listed below.

### Equivalence notes

<!-- BENCH:NOTES -->
- **hand-written** is plain constructor calls with module-level singletons (S4 uses a minimal dict-backed per-request cache). It is the floor: no container, no resolution.
- **wireup**: transients and request-scoped services can only be resolved from a scope. S2, S3 and S6 resolve from one long-lived scope; S4 enters and exits a scope per operation; S5 enters a scope per call (what `inject_from_container` does).
- **dishka** has no transient lifetime: `cache=False` is its documented equivalent. All services except the request-scoped one are registered in `Scope.APP`.
- **svcs** caches every service per `Container`, so "transient" is a fresh `Container` per operation (the container construction is part of the measured cost).
- **that-depends**: S5 uses `@inject(scope=None)` (skips entering an inject scope on every call; the cheapest idiomatic form). S4 uses a `ContextResource` in `ContextScopes.REQUEST`.
- **injector**: request scope is a custom `Scope` (the documented extension point), not a built-in. **punq**, **kink** and **inject** have no request scope (n/a). **kink** and **inject** wire classes by mutating `__init__` / a global injector.
- **rodi**: S7 includes `build_provider()` (eager validation and wiring), so S7 and S7r are the same cost. **aioinject**: `SyncContainer` for S1-S5/S7, async `Container` for S6. **diwire**: S5 passes `diwire_resolver=` explicitly because creating any other `Container` clears its global fallback.
- **lagom** autowires unregistered classes as transients; the singletons and the 50-class chain are registered explicitly.
- **dependency-injector**: S6 uses providers in async mode; Factory/Singleton providers are declared once, as in its docs.
- S7 measures building the container; S7r additionally resolves the 50th service (a 50-deep chain), because some libraries defer work (graph analysis, code generation) to the first resolve.

## Where injectq is not the fastest

Generated from the same run, so it cannot drift from the tables:

<!-- BENCH:NOT_FASTEST -->
- **S1 cached singleton**: injectq is not fastest. dependency-injector takes 0.057 µs, injectq 0.083 µs (1.5x slower); injectq ranks 3 of 14.
- **S4 request scope: enter, resolve, exit**: injectq is not fastest. rodi takes 0.836 µs, injectq 0.968 µs (1.2x slower); injectq ranks 2 of 9.
- **S7 build container (50 services)**: injectq is not fastest. inject takes 13.9 µs, injectq 27.4 µs (2.0x slower); injectq ranks 2 of 14.
- **S7r build container + resolve 50-deep chain**: injectq is not fastest. inject takes 98.3 µs, injectq 251 µs (2.6x slower); injectq ranks 3 of 14.
<!-- /BENCH:NOT_FASTEST -->

Context to read these rows with:

- S1 is a dictionary-style lookup of an already built object. `dependency-injector` is compiled
  (Cython), so on a pure lookup it can beat any pure-Python container. The absolute difference
  is small; see the table.
- Libraries that make a scope the unit of work (for example wireup and dishka) can be faster than injectq at
  entering and leaving that scope or at injecting into a function; the table says by how much.
- If a row is missing from the list, injectq was the fastest DI library there on this run.

## HTTP benchmark

The micro-benchmarks measure the container alone. `benchmarks/http/` measures it inside a real
request: the same small FastAPI app for each library, served by one Uvicorn worker, hit by a
load generator.

- **singleton** endpoint: injects two long-lived services (`A`, `B`).
- **scoped** endpoint: a request-scoped graph of seven services (`C` to `I`), some requested
  several times in one handler, with a generator resource (sync) and an async-generator resource
  that are torn down at the end of the request.
- Before measuring, each app is started in a counting mode and checked: singletons built once,
  request-scoped services built once per request and torn down, 50 concurrent requests do not
  share request state. A library that fails is not measured.
- Plain FastAPI `Depends` and a hand-wired app without DI are included as reference points.

## Limitations

- **Micro-benchmarks.** They show the cost of the container, not of your application. Network, JSON
  serialization, database access and your own code usually dominate.
- **Author-written.** The scripts for each library were written by the injectq authors from that
  library's documentation. We tried to use each library idiomatically and list every deviation
  above, but a maintainer may know a faster way. Corrections are welcome as pull requests.
- **CPython only.** Numbers are for one CPython version and build (see Machine and versions). Other
  interpreters, free-threaded builds and other CPU architectures can reorder the results.
- **One machine, one day.** Absolute values depend on the CPU and its load; ratios are more
  portable than microseconds.
- **Features differ.** Libraries make different trade-offs (validation, async support, resource
  teardown, scopes). A faster result is not a better library for your needs.

## Reproduce

```bash
git clone https://github.com/10xhub/injectq && cd injectq

# 1. micro-benchmarks, injectq only (uses your current environment)
python benchmarks/run.py                      # prints a table, writes benchmarks/latest.json
python benchmarks/check.py                    # fails if S1-S6 are >20% slower than the baseline

# 2. cross-library comparison in an isolated venv with pinned versions
make bench-compare                            # installs benchmarks/compare/requirements.txt
PUBLISH=1 make bench-compare                  # also regenerates this page's tables and chart

# 3. HTTP benchmark (needs `oha` or `hey` on PATH for publishable numbers)
pip install -r benchmarks/http/requirements.txt -e .
python benchmarks/http/run_http.py
python benchmarks/compare/report.py --update-docs docs/benchmarks.md
```

Smoke test without waiting (numbers are meaningless, it only checks that everything runs):
`BENCH_REPEATS=3 BENCH_TARGET=0.001 python benchmarks/run.py`.

See `benchmarks/README.md` for every option.
